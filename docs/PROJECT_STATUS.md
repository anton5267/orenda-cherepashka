## Що виправлено в коді

- Запрошення Supabase Dashboard, що повертає на головну з `type=invite`, переходить на форму створення пароля до ініціалізації Auth. Підтримуються також recovery callbacks.
- Помилка `resetPasswordForEmail` більше не показує хибне повідомлення про успішне надсилання.
- На сторінках політик є надані власником назва ФОП та адреса для письмових звернень, пряма кнопка оператора <https://t.me/yts_nnn>, країна Україна й email `antonlistva47@gmail.com`. Звернення щодо заміни/повернення спрямовуються оператору; універсальні строки гарантії чи повернення не вигадували.
- Runtime canonical/Open Graph у статичній збірці зберігають адресу production після запуску React. Це перевірено браузерними тестами й живим Cloudflare preview. GitHub Pages тепер перенаправляє на production; Render показує Service Suspended; старий окремий Pages повернув 522 з noindex. Fly не вдалося перевірити через закрите з’єднання — це не доказ відсутності індексації.
- Додано read-only експорт даних і сценарій перевірки відновлення. Деталі, межі та команди: [Supabase backup](../supabase/BACKUP.md).
- Початковий порожній стан форми більше не стирає `product`/`plan` з URL до завантаження каталогу. Автоматичний сценарій перевіряє перехід із товару, reload і зміну тарифу; живий production-сценарій також пройдено.

## Реалізована система

React/Vite/TypeScript-вітрина працює з окремим Supabase-проєктом `suzmndaqwchayddrulzc` (Frankfurt). Є каталог, категорії, пошук/сортування, тарифи за місяць/пакет, UTM та дата потреби, детальні сторінки товарів/новин, юридичні маршрути, теми, адаптивність і cookie-free аналітика з DNT/GPC. Адмінка містить огляд, товари, категорії, FAQ, новини, відгуки, заявки й налаштування.

Після збереження заявки показується номер; за збою API інтерфейс прямо повідомляє, що заявку не збережено, і може підготувати текст Telegram. Ці сценарії перевірені локально/з ізольованими відповідями API; вони не є доказом production-запису.

Контакти мають різні призначення: підтримка `@yts_nnn`, новини `@arenda_cherepashka`, відгуки `@cherepashka_vidguk`. Новини читаються з відкритого каналу; миттєвий Telegram webhook лишається опціональним і не налаштований без бота/секретів. Вигаданих відгуків не імпортували.

Express/SQLite/Docker — альтернативний режим, а не production-база Pages. Його щоденні SQLite-копії не захищають Supabase.

## Перевірки коду

`npm run ci:verify` пройшов локально раніше; обидва повні CI-прогони [PR №10](https://github.com/anton5267/orenda-cherepashka/pull/10) та main CI для `de9aed7` успішні. Окремо пройшли `npm run self-qa:auth-recovery`, typecheck та Cloudflare browser QA з runtime canonical/Open Graph перевірками. Браузерні сценарії охоплюють ширини 320, 375, 390, 768, 1024, 1440 та 1920 px. Це не сертифікація WCAG.

Причиною попереднього збою **Supabase Preview на main** (`site_settings already exists`) був порожній журнал міграцій за наявної схеми. Production порівняно з ізольованим PostgreSQL: таблиці, колонки, constraints, індекси, RLS, grants і дві application functions збігаються (для тіл функцій нормалізовано лише відступи). Через Dashboard виконано еквівалент запису історії `migration repair --status applied`: записано версії `20261015115335` і `20261015134209` з оригінальним SQL як текстом. Транзакція перевіряла точний актуальний manifest і порожню історію; application DDL та дані не виконувалися/не змінювалися. Результат — два рядки історії. Наступні Supabase checks для `main` `7fe165b` і `720c129` успішні.

Обидва CI-прогони фінального head PR №7 та PR №8 пройшли. Попередні спроби виявили нестабільність існуючих локальних failure-injection сценаріїв (очікування нового запису після retry); одна локальна повторна перевірка зупинилася на імітації 503 товару. Той самий код згодом пройшов повні CI-прогони; причину нестабільності не оголошуємо усунутою.

MCP Supabase у цьому чаті досі відхиляє доступ до Orenda; власник зняв цю вимогу як умову запуску. Auth, налаштування (без розкриття значень секретів), RLS та кількості перевірені через авторизований Dashboard і read-only SELECT. Сторонню базу не змінювали.

## Що залишається

1. Дочекатися успішного читання sitemap у Search Console; за подальшої помилки аналізувати її деталі. Факт прийнятого подання не дорівнює успішному читанню/індексації.
2. Юридична перевірка опублікованих текстів і реєстраційних даних лишається окремим кроком. Конкретні умови заміни/повернення підтверджує оператор до оплати.
3. Експорт application backup зараз ручний. Повний Supabase CLI dump, автоматичний графік і друга зашифрована копія на окремому сховищі ще потребують налаштування. Див. [план відновлення](../supabase/BACKUP.md).
4. Контрольна production-заявка пропущена за рішенням власника. Не позначати її успішною; для перевірки запису потрібен новий дозвіл.
5. Фізичний телефон і повний аудит доступності/старого Fly не перевірялися. Для цього приймання власник погодив ПК, старий GitHub Pages дублікат усунуто.

Сайт працює на основній адресі. Незакриті пункти вище не слід видавати за перевірені: насамперед звіт Google про sitemap, юридична оцінка текстів і автоматизація повнішої резервної копії.
