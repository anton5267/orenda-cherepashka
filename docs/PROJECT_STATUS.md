# Orenda Cherepashka: production-приймання

Оновлено **16 жовтня 2026 року**. Репозиторій: [anton5267/orenda-cherepashka](https://github.com/anton5267/orenda-cherepashka), `main`.

## Поточний висновок

Основну проблему розгортання усунуто: Cloudflare Pages розгортає `main` як **production**, автоматичні деплої увімкнені. Прямі маршрути на <https://orenda-cherepashka-live.pages.dev/> повертають HTTP 200. Виправлення запрошення власника та контакти підтримки злиті через [PR №6](https://github.com/anton5267/orenda-cherepashka/pull/6), SEO/backup — [PR №7](https://github.com/anton5267/orenda-cherepashka/pull/7), перенаправлення GitHub Pages — [PR №8](https://github.com/anton5267/orenda-cherepashka/pull/8). Для `main` `720c129` Cloudflare та Supabase checks успішні.

Повне production-приймання ще не завершене. Автентифікована панель і збереження/відновлення налаштувань перевірені. Google Live Test підтвердив доступ до sitemap, але звіт sitemap ще не показав успішного читання. Власник надав для публікації назву ФОП «Оренда акаунтів-CHEREPASHKA» та адресу: Мельницька вулиця, 32 б, Одеса, Одеська область, Україна, 65125. Реєстраційні відомості та юридичну відповідність текстів незалежно не перевіряли; конкретні гарантії погоджуються з оператором до оплати. **Власник відмовився від контрольної production-заявки — її не створювали і повторно без нового дозволу не створювати.**

`.shop`, старі GitHub Pages/Render/Fly, `orenda-cherepashka.pages.dev` та сторонній Supabase `german-ai-trainer` не використовуються для цього запуску.

## Що виправлено в коді

- Запрошення Supabase Dashboard, що повертає на головну з `type=invite`, переходить на форму створення пароля до ініціалізації Auth. Підтримуються також recovery callbacks.
- Помилка `resetPasswordForEmail` більше не показує хибне повідомлення про успішне надсилання.
- На сторінках політик є надані власником назва ФОП та адреса для письмових звернень, пряма кнопка оператора <https://t.me/yts_nnn>, країна Україна й email `antonlistva47@gmail.com`. Звернення щодо заміни/повернення спрямовуються оператору; універсальні строки гарантії чи повернення не вигадували.
- Runtime canonical/Open Graph у статичній збірці зберігають адресу production після запуску React. Це перевірено браузерними тестами й живим Cloudflare preview. GitHub Pages тепер перенаправляє на production; Render показує Service Suspended; старий окремий Pages повернув 522 з noindex. Fly не вдалося перевірити через закрите з’єднання — це не доказ відсутності індексації.
- Додано read-only експорт даних і сценарій перевірки відновлення. Деталі, межі та команди: [Supabase backup](../supabase/BACKUP.md).

## Реалізована система

React/Vite/TypeScript-вітрина працює з окремим Supabase-проєктом `suzmndaqwchayddrulzc` (Frankfurt). Є каталог, категорії, пошук/сортування, тарифи за місяць/пакет, UTM та дата потреби, детальні сторінки товарів/новин, юридичні маршрути, теми, адаптивність і cookie-free аналітика з DNT/GPC. Адмінка містить огляд, товари, категорії, FAQ, новини, відгуки, заявки й налаштування.

Після збереження заявки показується номер; за збою API інтерфейс прямо повідомляє, що заявку не збережено, і може підготувати текст Telegram. Ці сценарії перевірені локально/з ізольованими відповідями API; вони не є доказом production-запису.

Контакти мають різні призначення: підтримка `@yts_nnn`, новини `@arenda_cherepashka`, відгуки `@cherepashka_vidguk`. Новини читаються з відкритого каналу; миттєвий Telegram webhook лишається опціональним і не налаштований без бота/секретів. Вигаданих відгуків не імпортували.

Express/SQLite/Docker — альтернативний режим, а не production-база Pages. Його щоденні SQLite-копії не захищають Supabase.

## Перевірки коду

`npm run ci:verify` пройшов локально; [CI PR №6](https://github.com/anton5267/orenda-cherepashka/actions/runs/38888154403) також успішний. Окремо пройшли `npm run self-qa:auth-recovery`, typecheck та Cloudflare browser QA з runtime canonical/Open Graph перевірками. Існуючі браузерні сценарії охоплюють ширини 320, 375, 390, 768, 1024, 1440 та 1920 px. Це не повне приймання на фізичних телефонах і не сертифікація WCAG.

Причиною попереднього збою **Supabase Preview на main** (`site_settings already exists`) був порожній журнал міграцій за наявної схеми. Production порівняно з ізольованим PostgreSQL: таблиці, колонки, constraints, індекси, RLS, grants і дві application functions збігаються (для тіл функцій нормалізовано лише відступи). Через Dashboard виконано еквівалент запису історії `migration repair --status applied`: записано версії `20261015115335` і `20261015134209` з оригінальним SQL як текстом. Транзакція перевіряла точний актуальний manifest і порожню історію; application DDL та дані не виконувалися/не змінювалися. Результат — два рядки історії. Наступні Supabase checks для `main` `7fe165b` і `720c129` успішні.

Обидва CI-прогони фінального head PR №7 та PR №8 пройшли. Попередні спроби виявили нестабільність існуючих локальних failure-injection сценаріїв (очікування нового запису після retry); одна локальна повторна перевірка зупинилася на імітації 503 товару. Той самий код згодом пройшов повні CI-прогони; причину нестабільності не оголошуємо усунутою.

MCP Supabase досі відхиляє доступ до Orenda. Auth, секрети (лише digest), RLS та кількості перевірені через авторизований Dashboard і read-only SELECT. Сторонню базу не змінювали.

## Що залишається

1. Завершити реальне email-recovery за потреби власника. Login/logout/relogin, автентифіковану панель і збереження/повернення безпечної зміни вже перевірено. Не просити пароль у чаті.
2. Власник надав назву ФОП та адресу для публікації; контакти заповнені. Конкретні умови заміни/повернення підтверджує оператор до оплати. Юридична перевірка текстів лишається окремим кроком.
3. Дочекатися успішного читання sitemap у Search Console; за подальшої помилки аналізувати її деталі. Факт прийнятого подання не дорівнює успішному читанню/індексації.
4. Експорт application backup зараз ручний. Повний Supabase CLI dump, автоматичний графік і друга зашифрована копія на окремому сховищі ще потребують налаштування. Див. [план відновлення](../supabase/BACKUP.md).
5. Під час наступних змін зберігати перевірки міграцій: історію вже синхронізовано, наступні main checks пройшли.
6. Ручне приймання на фізичних пристроях/браузерах, слабка мережа та повний SEO-аудит недоступного Fly ще не закриті. GitHub Pages дублікат усунуто.
7. Контрольна production-заявка пропущена за рішенням власника. Не позначати її успішною; для перевірки запису потрібен новий дозвіл.

Повністю завершений запуск означає підтверджений доступ власника, погоджені юридичні умови, читання sitemap, перевірений production-запис (якщо власник дозволить) і виконувану стратегію резервування. Наявні результати не підмінюють ці незавершені пункти.
