# Orenda Cherepashka: стан проєкту та план запуску

Оновлено: **16 жовтня 2026 року**. Джерело коду: [`anton5267/orenda-cherepashka`](https://github.com/anton5267/orenda-cherepashka), гілка `main`. Це інвентаризація фактично виконаної роботи, а не твердження, що магазин уже повністю запущений.

## Короткий висновок

Застосунок, каталог, публічний API, адмін-інтерфейс і автоматичне читання новин із публічного Telegram-каналу реалізовані. GitHub CI проходить. Але **основна адреса Cloudflare Pages ще не показує актуальну збірку на всіх маршрутах**, **вхід власника в адмінку не перевірений** і **жодну реальну production-заявку не тестували**. Тому статус — **технічно підготовлено, але не завершено production-приймання**.

Основна запланована адреса — <https://orenda-cherepashka-live.pages.dev/>. Адреса <https://main.orenda-cherepashka-live.pages.dev/> — попередній перегляд гілки `main`, а не остаточна production-адреса. Старий домен `.shop` свідомо **не підключаємо**. Старі GitHub Pages/Render/Fly та окремий Pages-проєкт `orenda-cherepashka.pages.dev` не є джерелом актуальних заявок.

### Що вже реалізовано

- Каталог із пошуком, категоріями, сортуванням, станом пропозицій, вибором тарифів і формою заявки. Враховано варіанти ціни за місяць та за пакет: наприклад, Grok Super особистий — **800 грн за місяць або 2 200 грн за пакет на 3 місяці**, а не 2 200 грн щомісяця.
- За даними попереднього імпорту Supabase: 35 товарів, 62 цінові варіанти, шість категорій і п'ять FAQ. Публічний API 16.10.2026 віддав **30 активних товарів**; п'ять неактивних пропозицій не показуються. Кількості в базі взято з журналу розгортання; прямий доступ до БД через поточний ChatGPT-конектор відсутній.
- Після успішної заявки інтерфейс показує її номер і контакт із продавцем. За збою API він прямо повідомляє, що заявку **не збережено**, і пропонує підготувати текст для Telegram. Є поле «Коли потрібна підписка?» та UTM-атрибуція. Реальну production-заявку й появу її в адмінці ще не перевірено.
- Розділи адмінки: огляд/аналітика, товари, категорії, FAQ, новини, відгуки, заявки й налаштування. Є відновлення пароля; публічну реєстрацію вимкнено. Сам факт наявності форми входу **не доводить**, що власник уже може ввійти.
- У налаштуваннях за замовчуванням контактні кнопки ведуть до <https://t.me/yts_nnn>; канал новин — <https://t.me/arenda_cherepashka>; канал відгуків — <https://t.me/cherepashka_vidguk>. Це три різні призначення, їх не слід змішувати. Налаштування, збережені в production-базі, потрібно додатково перевірити після входу в адмінку.
- Публічний API читає відкриту сторінку Telegram-каналу і коротко кешує результат. 16.10.2026 API повернув **7 новин**; за попередньою перевіркою це шість постів каналу та одна ручна новина. Новина не з'явиться, якщо в самому каналі немає нового поста: на останній попередній перевірці найновіший був від 17.09.2026. Код webhook для миттєвої доставки й редагувань є, але без бота/секретів він **не ввімкнений**.
- Відгуки на вітрині посилаються на реальний канал. Вигадані оцінки не публікували; модерація відгуків передбачена, але імпорт підтверджених відгуків не завершений.
- У коді є світла/темна тема із системним вибором, початкове застосування теми до завантаження React, адаптивні меню/форми/картки, видимі focus-стани й підтримка `prefers-reduced-motion`. Автоматизовані браузерні тести перевіряють ширини **320, 375, 390, 768, 1024, 1440 та 1920 px**, зокрема горизонтальне переповнення. Це не є повним ручним аудитом WCAG 2.2 AA на реальних пристроях.
- Є сторінки товарів `/p/:slug`, новин `/news/:id`, юридичних текстів `/legal/*`, `robots.txt`, `sitemap.xml`, canonical/Open Graph та структуровані дані. Для резервної GitHub Pages-версії передбачено `noindex`/canonical. Сторінки політик — технічні чернетки без реквізитів продавця та юридичної перевірки.
- Реалізовано валідацію й ліміти для заявок, закритий адмін-API з JWT і email allowlist, RLS-міграції та окрему перевірку секрету Telegram webhook. У локальному Express-режимі є додаткові security headers; їхній фактичний набір на Cloudflare production треба перевіряти окремо. Секрети не слід розміщувати у Git або змінних `VITE_*`.
- Є cookie-free аналітика сторінок, товарів, переходів у Telegram, заявок та UTM; код враховує Do Not Track / Global Privacy Control. Реальні production-цифри без входу власника не перевірені.
- Для **локальної SQLite-бази** є щоденні резервні копії з ротацією та сценарій відновлення. Це **не резервна копія Supabase Postgres**; для production-даних потрібна окрема перевірена стратегія експорту/відновлення.
- Офіційні Supabase Agent Skills додані в репозиторій і злиті в `main` через [PR №4](https://github.com/anton5267/orenda-cherepashka/pull/4). Вони допомагають майбутній розробці, але самі не надають доступ до Supabase.

Декілька окремих HTTP-запитів до health/sitemap під час повторної перевірки отримали `ECONNRESET`; це не доказ помилки сервера і не записано як успішну перевірку. Попередні журнали проєкту містять успішні health 200, CORS 204, unauthenticated admin 401 і неактивний webhook 503, але ці конкретні результати **не повторювалися успішно в цій перевірці**. Google Search Console раніше підтвердила власність Pages-ресурсу та індексацію головної; її поточний звіт sitemap з цього середовища не перевірено.

## Що ще треба зробити — у порядку пріоритету

### P0 — перед реальним запуском

1. **Зробити `main` production-гілкою Cloudflare Pages.** У проєкті `orenda-cherepashka-live`: **Settings → Builds & deployments → Configure Production deployments** → вибрати `main`, увімкнути автоматичні production-розгортання і зберегти. Після нової збірки перевірити `/`, `/admin/login`, `/admin/reset-password`, одну `/p/:slug`, `/news/:id`, `/legal/privacy`, `/robots.txt` та `/sitemap.xml` саме на `orenda-cherepashka-live.pages.dev`. [Cloudflare: branch deployment controls](https://developers.cloudflare.com/pages/configuration/branch-build-controls/).
2. **Створити/підтвердити власника у Supabase Auth** через Dashboard Authentication → Users або офіційний Auth Admin invite, використавши email, який відповідає server-side `ADMIN_EMAIL`. Власник сам задає пароль із листа; пароль не передавати в чат чи репозиторій. Далі перевірити login, logout, password recovery і збереження одного безпечного тестового редагування. Публічну реєстрацію залишити вимкненою. [Supabase: запрошення користувача](https://supabase.com/docs/reference/javascript/auth-admin-inviteuserbyemail).
3. **Заповнити реквізити продавця й переглянути юридичні тексти**: ім'я/ФОП або іншу форму діяльності, країну/адресу для звернень, email/телефон за потреби, чіткі гарантії та умови заміни/повернення для різних сервісів. Без цього сторінки політик лишаються чернеткою; не оголошувати їх юридично завершеними.
4. **Провести контрольну production-заявку за згодою власника** з тестовими даними: сайт → API → номер заявки → адмінка → статус заявки. Перевірити також сценарій недоступного API, щоб незбережена чернетка не видавалася за прийняте замовлення. Тестові персональні дані не використовувати.

### P1 — стабільність і автоматизація

5. **Перевірити sitemap у Google Search Console** після виправлення production-гілки: доступність XML з основної адреси, правильні абсолютні URL, повторне надсилання sitemap та подальшу індексацію. Попередній звіт показував `Couldn't fetch`; не позначати SEO як завершене, поки статус не зміниться.
6. **Визначити режим оновлення Telegram-новин.** Публічне читання каналу вже працює. Для регулярної перебудови статичного snapshot потрібні Cloudflare Pages Deploy Hook і GitHub Actions secret `CLOUDFLARE_PAGES_BUILD_HOOK`; зараз secret не налаштований, тому запуск workflow із `success` може означати лише повідомлення «налаштуйте hook», а не новий deploy. Для миттєвого webhook окремо потрібен бот-адміністратор каналу та `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_CHANNEL_ID` у Supabase. Це опціонально для читання публічного каналу. [Cloudflare: Deploy Hooks](https://developers.cloudflare.com/pages/configuration/deploy-hooks/).
7. **Налаштувати production-відновлення даних.** Перевірити доступний для поточного плану спосіб експорту Supabase Postgres, зберігання копій окремо від проєкту та пробне відновлення. Локальні SQLite-копії не захищають Supabase-дані. На Free-плані неактивний проєкт може бути призупинений; [офіційна довідка](https://supabase.com/docs/guides/platform/free-project-pausing).
8. **Пройти ручне приймання на реальних пристроях і браузерах**: мобільне меню, пошук/фільтри, довгі назви товарів, форма з екранною клавіатурою, доступність клавіатурою й контраст, слабка мережа, порожній каталог, невідомий slug, завантаження медіа та консольні помилки. CI покриває частину сценаріїв, але не замінює це приймання.

### Окремий доступ для подальшої роботи агента

ChatGPT-конектор Supabase наразі **не має доступу до організації Orenda**. Потрібна авторизація саме цієї організації у підключенні MCP; простий вхід у Supabase через Google/ChatGPT не дорівнює дозволу конектору. Це блокує роботу агента з базою, але **не є причиною 404 Cloudflare** і само по собі не зупиняє публічний API. Підключення до стороннього `german-ai-trainer` не використовувати. [Supabase MCP](https://supabase.com/docs/guides/ai-tools/mcp).

## Інструкція для нового розробника

1. Працювати з Git-репозиторієм `anton5267/orenda-cherepashka`, а не зі старим ZIP-знімком чи `.shop`-сайтом.
2. Встановити залежності: `npm ci`. Для повної локальної перевірки: `npm run ci:verify`. Для Cloudflare потрібні `PUBLIC_SITE_URL`, `VITE_SUPABASE_URL` і **лише публічний** `VITE_SUPABASE_PUBLISHABLE_KEY`; збірка `npm run build:cloudflare`, каталог `dist`.
3. Для локального Express/SQLite-режиму читати [README](../README.md). Для Supabase/Cloudflare-конфігурації — [runbook](../supabase/DEPLOYMENT.md). Не змішувати SQLite backup і Supabase Postgres.
4. Перед змінами в схемі переглянути міграції в `supabase/migrations/` і RLS. Не створювати Auth-користувачів SQL-записом у `auth.users`; використовувати Supabase Auth. Не публікувати `service_role`, токени Telegram, deploy hook або паролі.
5. Після кожного деплою повторювати браузер → API → база → відповідь і фіксувати **окремо** локальні, preview та production-результати.

## Критерій «готово»

Production Pages розгортає `main`; усі прямі маршрути й sitemap працюють на основному Pages-хості; власник входить до адмінки та редагує дані; контрольна заявка з'являється в адмінці; юридичні дані продавця й умови погоджені; Search Console читає sitemap; є перевірений план резервного копіювання Supabase. Лише після цих підтверджень вважати публічний запуск завершеним.
